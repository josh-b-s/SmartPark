# SmartPark - FastAPI + YOLO parking detection service

Real-time-ish car park availability, served over a REST API, backed by a
YOLO model that detects empty vs occupied spaces in camera images.

## Run it locally

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Then try:
```bash
curl "http://127.0.0.1:8000/api/find-carparks?uuid=abc-123&n=3"
curl "http://127.0.0.1:8000/api/annotate-carpark?carpark_id=CBD_001"
curl "http://127.0.0.1:8000/api/ops/carparks"
curl "http://127.0.0.1:8000/api/ops/active-users"
```

Interactive docs (auto-generated by FastAPI) at http://127.0.0.1:8000/docs

To see an annotated image rather than raw base64 text, run:
```bash
python view_annotated.py CBD_001
```
and open the resulting `annotated_CBD_001.png`.

## What's implemented (CORE-API-1/2, OPS-API-1/2, OPS-REQ-1)

- `GET /api/find-carparks?uuid=&n=`: samples `2*n` random carparks, runs
  YOLO inference on each concurrently, returns the top `n` by available
  spaces. Clamps `n` to `MAX_N` (see config.py) instead of erroring, as a
  first answer to the spec's "what if n > 100?" prompt.
- `GET /api/annotate-carpark?carpark_id=`: returns a base64 PNG with YOLO
  bounding boxes drawn on the detected spaces.
- `GET /api/carparks/{carpark_id}/takephoto`: simulates a carpark's own
  camera. Returns a random image from the configured image folder, or a
  generated placeholder if none are found.
- `GET /api/ops/carparks`: OPS-API-1.
- `GET /api/ops/active-users`: OPS-API-2, backed by an in-memory request
  log (`app/request_log.py`) that OPS-REQ-1 asked for.
- `GET /ops/dashboard`: a matplotlib-rendered PNG dashboard, see below.
- `GET /healthz`: liveness/readiness probe target for Kubernetes.

## Real YOLO inference

`app/model.py` loads the model lazily on first use from `model/model.pt`
(configurable via `SMARTPARK_MODEL_PATH`). Drop your trained weights in at
`model/model.pt` to activate real inference. Until then, the app
automatically falls back to `carparks.fake_inference()` (random numbers)
so everything still runs end-to-end without the weights file.

Class convention (matches the PKLot label conversion in the training
notebook): class 0 = empty/available, class 1 = occupied. Configurable via
`SMARTPARK_EMPTY_CLASS_ID` if you retrain with different label order.

`carparks.infer_carpark(carpark_id)` is the blocking entry point: it takes
a photo, then either runs real YOLO inference or the random fallback.
`main.py` always calls it via `asyncio.to_thread(...)`, and `asyncio.gather`
for the `2*n` sampled carparks in `find-carparks`, so they run concurrently
rather than one at a time. This is the spec's explicit warning about not
blocking the event loop with synchronous CPU-bound YOLO calls.

## Ops dashboard

`GET /ops/dashboard` returns a PNG: a bar chart of available spaces per
carpark from OPS-API-1's data, plus active user and total request counts
from the OPS-REQ-1 log. Rendered server-side with matplotlib on each
request, just reload the URL in a browser to refresh it. Uses the same
fake_inference() data as OPS-API-1, for the same scalability reason noted
below, not real per-carpark YOLO inference on every dashboard load.

## Design notes / things to raise at the interview

- **Carparks are simulated in-process**, not as separate services. Each
  "carpark" is just a dict entry (`app/carparks.py`); its `/takephoto` is a
  route on the same FastAPI app rather than a genuinely separate camera
  device. This satisfies the API shape the spec asks for while staying
  simple, worth being able to explain and justify this choice in the
  interview.
- **Request log is in-memory** (`app/request_log.py`), which is fine for a
  single pod but means OPS-API-2 gives a per-pod view once you scale to
  multiple replicas. Call this out as a known limitation in the report;
  the real fix (shared store like Redis) is out of scope for now.
- **`/api/ops/carparks` and `/ops/dashboard` use fake_inference()**, not
  real YOLO, because running inference on up to 99 carparks on every ops
  call or dashboard refresh doesn't scale. The real fix is a background
  task that periodically refreshes a cache per carpark. This doubles as
  the "cache repeated requests" perf optimisation the spec asks about,
  just not implemented yet.

## Run with Docker

Build the image (run this from the project root, the folder containing
Dockerfile, app/, images/):

```bash
docker build -t smartpark-api .
```

Run it, mounting your trained model weights from the host so they are not
baked into the image. This satisfies the "updatable model" requirement:
swap the weights file and restart the container, no rebuild needed.

```bash
docker run -p 8000:8000 -v "$(pwd)/model:/app/model" smartpark-api
```

On Windows (PowerShell):

```powershell
docker run -p 8000:8000 -v "${PWD}\model:/app/model" smartpark-api
```

If you don't mount a model directory, the container still runs fine. It
falls back to the same random-number stub used locally when no
`model.pt` is present.

The `HEALTHCHECK` in the Dockerfile hits `/healthz`. Check container
health with `docker ps`, the STATUS column should say "healthy" after
about 10 seconds.

Note on image size: `ultralytics` pulls in `torch`, so the built image
will be a few hundred MB to a couple GB depending on platform. That's
expected and fine for local Docker testing, but worth knowing before
pushing it to a container registry on a slow connection, since pull time
counts against GKE session cost.

## Deploy to GKE

See `gcp/commands.md` for the full copy-paste command sequence (project
setup, image push, cluster creation, deploy) and `gcp/teardown.md` for
what to run at the end of every session to avoid unnecessary billing.

Key design point: like the local Docker setup, `model.pt` is not baked
into the image. `k8s/deployment.yaml` uses an init container that
downloads it from a GCS bucket into a shared volume before the main
container starts. Swapping the model means re-uploading to the bucket and
restarting the deployment (`kubectl rollout restart deployment
smartpark-api`), not rebuilding the image.

`k8s/hpa.yaml` (autoscaling) is included but should NOT be applied until
after Locust benchmarking at fixed replica counts is done. See the
comment at the top of that file for why, and use `kubectl scale
deployment smartpark-api --replicas=N` to control replica count manually
during benchmarking instead.
