# SmartPark - Step 1/2: FastAPI skeleton with YOLO inference

This is deliberately the *simplest possible version* of the whole system:
all endpoints exist and return the right JSON shapes, but `available_spaces`
/ `confidence_score` come from `carparks.fake_inference()` (random numbers,
not YOLO. The point of this step is to lock down the API contract and
request flow before ML/Docker/K8s complexity gets layered on.

## Run it

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Then try:
```bash
curl "http://127.0.0.1:8000/api/find-carparks?uuid=abc-123&n=3"
curl "http://127.0.0.1:8000/api/annotate-carpark?carpark_id=CBD_001"
curl "http://127.0.0.1:8000/api/ops/carparks"
curl "http://127.0.0.1:8000/api/ops/active-users"
```

Interactive docs (auto-generated by FastAPI) at http://127.0.0.1:8000/docs

## What's implemented (CORE-API-1/2, OPS-API-1/2, OPS-REQ-1)

- `GET /api/find-carparks?uuid=&n=` samples `2*n` random carparks,
  returns the top `n` by available spaces. Clamps `n` to `MAX_N` (see
  config.py) instead of erroring, as a first answer to the spec's
  "what if n > 100?" prompt.
- `GET /api/annotate-carpark?carpark_id=` returns a base64 image
  (currently just the raw camera frame, no bounding boxes yet).
- `GET /api/carparks/{carpark_id}/takephoto` simulates a carpark's own
  camera. Returns a random image from `app/data/sample_images/` if you've
  put some there, otherwise a generated placeholder PNG.
- `GET /api/ops/carparks`: OPS-API-1.
- `GET /api/ops/active-users`: OPS-API-2, backed by an in-memory request
  log (`app/request_log.py`) that OPS-REQ-1 asked for.
- `GET /healthz`: added early so it's not forgotten for the K8s
  liveness/readiness probes later.

## Design notes / things to raise at the interview

- **Carparks are simulated in-process**, not as separate services. Each
  "carpark" is just a dict entry (`app/carparks.py`); its `/takephoto` is a
  route on the same FastAPI app rather than a genuinely separate camera
  device. This satisfies the API shape the spec asks for while staying
  simple, worth being able to explain and justify this choice in the
  interview.
- **Request log is in-memory** (`app/request_log.py`), which is fine for a
  single pod but means OPS-API-2 gives a per-pod view once you scale to
  multiple replicas. Call this out as a known limitation in the report;
  the real fix (shared store like Redis) is out of scope for now.
- **`fake_inference()` is a marked stub** in `carparks.py`. That's exactly
  where step 2 plugs in real YOLO inference, wrapped in
  `asyncio.to_thread`/`run_in_threadpool` so it doesn't block the event
  loop under concurrent load (per the spec's explicit warning).

## Step 2: real YOLO inference - done

`app/model.py` loads the model lazily on first use from `model/model.pt`
(configurable via `SMARTPARK_MODEL_PATH`). **Drop your trained weights in
at `smartpark/model/model.pt` to activate real inference**. Until then,
the app automatically falls back to `carparks.fake_inference()` (random
numbers) so everything still runs end-to-end without the weights file.

Class convention (matches the PKLot label conversion in the training
notebook): **class 0 = empty/available, class 1 = occupied**. Configurable
via `SMARTPARK_EMPTY_CLASS_ID` if you retrain with different label order.

`carparks.infer_carpark(carpark_id)` is the blocking entry point. It takes
a photo, then either runs real YOLO inference or the random fallback.
`main.py` always calls it via `asyncio.to_thread(...)` (and `asyncio.gather`
for the `2*n` sampled carparks in `find-carparks`, so they run concurrently
rather than one at a time). This is the spec's explicit warning about not
blocking the event loop with synchronous CPU-bound YOLO calls.

`reference/teaching_team_reference_main.py` is the unmodified example
snippet the unit gave us for loading/using the model, kept for reference,
not imported by the app.

**Known limitation to flag in the report:** `OPS-API-1` (`/api/ops/carparks`)
still uses fake_inference for all carparks rather than real YOLO, because
running inference on up to 99 carparks on every dashboard refresh doesn't
scale. The real fix is a background task that periodically refreshes a
cache per carpark. This doubles as the "cache repeated requests" perf
optimisation the spec asks about, just not implemented yet.

## Run with Docker (step 4)

Build the image (run this from the project root, the folder containing
Dockerfile, app/, images/):

```bash
docker build -t smartpark-api .
```

Run it, mounting your trained model weights from the host so they are not
baked into the image. This satisfies the "updatable model" requirement:
swap the weights file and restart the container, no rebuild needed.

```bash
docker run -p 8000:8000 -v "$(pwd)/model:/app/model" smartpark-api
```

On Windows (PowerShell):

```powershell
docker run -p 8000:8000 -v "${PWD}\model:/app/model" smartpark-api
```

If you don't mount a model directory, the container still runs fine. It
falls back to the same random-number stub used locally when no
`model.pt` is present.

Test it the same way as before, just against the container instead of a
local uvicorn process:

```bash
curl "http://127.0.0.1:8000/api/find-carparks?uuid=abc-123&n=3"
```

The `HEALTHCHECK` in the Dockerfile hits `/healthz`. Check container health
with:

```bash
docker ps
```

Look at the STATUS column, it should say "healthy" after about 10 seconds.

Note on image size: `ultralytics` pulls in `torch`, so the built image
will be a few GB. That is expected and fine for local Docker testing, but
worth knowing before pushing it to a container registry on a slow
connection or worrying about GKE pull times.
