# SmartPark - FastAPI + YOLO parking detection service

Real-time-ish car park availability, served over a REST API, backed by a
YOLO model that detects empty vs occupied spaces in camera images.

## Files not included in this zip

Two large inputs are deliberately left out to keep the archive small. Add
them before running or building:

- **`images/`** (about 200 MB): the sample car park photos from the teaching
  team's release. Put the `.jpg` / `.png` files directly in `images/` in the
  project root. The Dockerfile copies this folder into the image, so it must
  exist when you run `docker build` (an empty folder is enough to build; the
  app then serves generated placeholder images from `/api/takephoto`).
- **`model/model.pt`** (about 3 GB): the trained YOLO weights. For local runs
  and `docker run`, place the file at `model/model.pt`. For GKE, upload it to
  the model bucket (`gsutil cp model/model.pt gs://YOUR_BUCKET/model.pt`, see
  `gcp/commands.md` step 3); the pod's init container downloads it at startup.
  Without a model file the app still starts but returns random fallback
  numbers, and the log says so (`YOLO weights not found`).

## Run it locally

```bash
pip install -r requirements.txt
uvicorn app.main:app --port 8000
```

Keep the port at 8000. The platform fetches each car park's image with an
HTTP GET to a camera URL that defaults to `http://127.0.0.1:8000`. If you run
on another port, set `SMARTPARK_CAMERA_BASE_URL` to match (for example
`SMARTPARK_CAMERA_BASE_URL=http://127.0.0.1:9000`).

Then try:
```bash
curl "http://127.0.0.1:8000/api/find-carparks?uuid=abc-123&n=3"
curl "http://127.0.0.1:8000/api/annotate-carpark?carpark_id=CBD_001"
curl "http://127.0.0.1:8000/api/ops/carparks"
curl "http://127.0.0.1:8000/api/ops/active-users"
curl "http://127.0.0.1:8000/api/takephoto?carpark_id=CBD_001"   # the simulated camera itself
```

Interactive docs (auto-generated by FastAPI) at http://127.0.0.1:8000/docs

To see an annotated image rather than raw base64 text, run:
```bash
python view_annotated.py CBD_001
```
and open the resulting `annotated_CBD_001.png`.

## What's implemented (CORE-API-1/2, OPS-API-1/2, OPS-REQ-1/2)

- `GET /api/find-carparks?uuid=&n=`: samples `2*n` random carparks,
  fetches each one's image with an HTTP GET to its camera, runs YOLO
  inference concurrently, and returns the top `n` by available spaces.
  Clamps `n` to `MAX_N` (see config.py) instead of erroring, as a first
  answer to the spec's "what if n > 100?" prompt. If some cameras fail it
  answers from the rest (`msg` says how many failed); if all fail it
  returns HTTP 503 with `status: "error"`. Repeat requests with the same
  `uuid` and `n` can be served from a short-lived cache
  (`SMARTPARK_USER_CACHE_TTL`, off by default, see below).
- `GET /api/annotate-carpark?carpark_id=`: returns a base64 PNG with YOLO
  bounding boxes drawn on the detected spaces (HTTP 502 if the camera is
  unreachable).
- `GET /api/takephoto?carpark_id=`: the simulated car park camera. Returns a
  random image from the configured image folder, or a generated placeholder
  if none are found. The platform reaches it over HTTP via each car park's
  `camera_url`, so this is the "HTTP GET to the camera" step in the
  architecture diagram.
- `GET /api/ops/carparks`: OPS-API-1. Latest available-spaces reading per
  carpark, with `confidence_score`, `last_updated` and `source` (`yolo`, or
  `fallback_random` when no model file is loaded). `available_spaces` is
  `null` until a carpark's first reading exists.
- `GET /api/ops/active-users`: OPS-API-2, backed by an in-memory request
  log (`app/request_log.py`) that OPS-REQ-1 asked for.
- `GET /ops/dashboard`: a matplotlib-rendered PNG dashboard, see below.
- `GET /healthz`: liveness/readiness probe target for Kubernetes.

## Configuring car parks and caching

All settings are environment variables. In Kubernetes they come from the
`smartpark-config` ConfigMap (`k8s/configmap.yaml`); after editing it, run
`kubectl apply -f k8s/configmap.yaml` and
`kubectl rollout restart deployment smartpark-api`.

| Variable | Default | Meaning |
|---|---|---|
| `SMARTPARK_NUM_CARPARKS` | 20 | Car parks to generate. Must be 10-99, otherwise the app refuses to start. |
| `SMARTPARK_CARPARK_CONFIG` | unset | Path to a JSON file that defines the car parks explicitly (below). |
| `SMARTPARK_CAMERA_BASE_URL` | `http://127.0.0.1:8000` | Base URL for generated car parks' cameras. |
| `SMARTPARK_MAX_N` | 20 | Largest `n` accepted by `find-carparks`. |
| `SMARTPARK_USER_CACHE_TTL` | 0 (off) | Seconds to cache a `find-carparks` answer per (`uuid`, `n`). |
| `SMARTPARK_OPS_REFRESH_SECONDS` | 60 | Background refresh interval for OPS-API-1 and the dashboard. 0 disables it. |
| `SMARTPARK_LOG_RETENTION` | 300 | Seconds of request-log history kept in memory. |

**Discovery and connection details.** Car parks are discovered at startup
from one of two places: generated (`CBD_001` to `CBD_0NN`, each with a
camera URL of `<SMARTPARK_CAMERA_BASE_URL>/api/takephoto?carpark_id=<id>`), or
listed in a JSON file. The JSON file is a list of 10-99 objects; only
`carpark_id` is required:

```json
[
  {"carpark_id": "MEL_01", "name": "Melbourne Central", "camera_url": "http://cam-01.internal/api/takephoto", "total_spaces": 120}
]
```

To use it in Kubernetes, add the JSON to `k8s/configmap.yaml` under a
`carparks.json: |` key, then in `k8s/deployment.yaml` mount it and point the
app at it:

```yaml
          env:
            - name: SMARTPARK_CARPARK_CONFIG
              value: /app/config/carparks.json
          volumeMounts:
            - name: carpark-config
              mountPath: /app/config
      volumes:
        - name: carpark-config
          configMap:
            name: smartpark-config
            items:
              - key: carparks.json
                path: carparks.json
```

(Merge these into the existing `env`, `volumeMounts` and `volumes` lists
rather than adding duplicates.) Locally, just set
`SMARTPARK_CARPARK_CONFIG=path/to/carparks.json`. Pointing a `camera_url` at
a different host needs no code change.

**Caching.** Two small per-pod caches live in `app/cache.py`:

- *Ops cache*: every inference result (from user requests or the
  background refresher) updates the latest reading per carpark. OPS-API-1
  and the dashboard only read this cache, so they never run YOLO
  themselves. The refresher re-checks only carparks whose reading is older
  than `SMARTPARK_OPS_REFRESH_SECONDS`, one at a time, so under user load it
  has almost nothing to do.
- *User cache*: with `SMARTPARK_USER_CACHE_TTL` above 0, a repeat
  `find-carparks` call with the same `uuid` and `n` is answered without
  fetching or inferring anything. It is off by default so that Locust
  benchmark runs (where each simulated user reuses one uuid) stay
  comparable. To demo it, set the ConfigMap value to e.g. `"10"`, restart,
  and call the same URL twice: `speed_inference` drops to well under a
  millisecond on the second call.

Both caches, like the request log, are per pod.

## Application logging (OPS-REQ)

Every request, on every endpoint, is logged as one structured line via a
FastAPI middleware in `main.py`: timestamp and severity from Python's
logging formatter, `smartpark` as the service name, plus a `request_id`
(the caller's own `uuid` query param when present, e.g. on
`find-carparks`, otherwise a generated one), method, path, status code,
and duration in ms. Unhandled exceptions are logged with a full traceback
via `logger.exception` before re-raising. On GKE this output goes to
stdout, which Cloud Logging picks up automatically, no extra
configuration needed.

## Real YOLO inference

`app/model.py` loads the model lazily on first use from `model/model.pt`
(configurable via `SMARTPARK_MODEL_PATH`). Drop your trained weights in at
`model/model.pt` to activate real inference. Until then, the app
automatically falls back to `carparks.fake_inference()` (random numbers)
so everything still runs end-to-end without the weights file.

Class convention (matches the PKLot label conversion in the training
notebook): class 0 = empty/available, class 1 = occupied. Configurable via
`SMARTPARK_EMPTY_CLASS_ID` if you retrain with different label order.

`carparks.infer_carpark(carpark_id)` is the async entry point: it fetches
the photo over HTTP (`fetch_photo`, non-blocking), then runs the blocking
`infer_image` in a worker thread via `asyncio.to_thread`, either real YOLO
inference or the random fallback. `find-carparks` uses `asyncio.gather`
across the `2*n` sampled carparks so they run concurrently rather than one
at a time. This is the spec's explicit warning about not blocking the event
loop with synchronous CPU-bound YOLO calls.

`find-carparks` passes `annotate=False`, which skips drawing and PNG-encoding
the annotated image (it is never returned by that endpoint). Only
`annotate-carpark` pays that cost. Note that the benchmark numbers in the
report were measured before this change, when every inference also rendered
the annotated image.

## Ops dashboard

`GET /ops/dashboard` returns a PNG: a bar chart of the latest available
spaces per carpark (the same cached readings as OPS-API-1), plus active user
and total request counts from the OPS-REQ-1 log. Rendered server-side with
matplotlib on each request, just reload the URL in a browser to refresh it.
If no model file is loaded the chart title says it is showing random fallback
data.

## Design notes / things to raise at the interview

- **Carparks and cameras are simulated in one app.** Each carpark is an entry
  in a registry (generated, or loaded from JSON) with a `camera_url`. The
  cameras are simulated by the app's own `GET /api/takephoto` route, but the
  platform reaches them with a real HTTP GET, so the code path is the same one
  a genuinely separate camera would use, and the URL can point elsewhere.
  Being simulated in-process means the loopback camera calls share the same
  pod CPU as inference, worth being able to explain.
- **Request log, ops cache and user cache are in memory, per pod.** Fine for
  a single pod, but once you scale to multiple replicas OPS-API-2's active
  user count and the ops readings only reflect requests that pod handled.
  The request log is pruned to `SMARTPARK_LOG_RETENTION` seconds (with a
  separate lifetime counter), so it doesn't grow without bound. The real fix
  for the per-pod views is a shared store such as Redis, out of scope here.
- **OPS-API-1 never runs inference itself.** It reads readings written by
  earlier inference, so it stays cheap with up to 99 carparks. The trade-off
  is that a reading can be up to about `SMARTPARK_OPS_REFRESH_SECONDS` old
  (or missing for a moment right after startup).

## Run with Docker

Build the image (run this from the project root, the folder containing
Dockerfile, app/, images/):

```bash
docker build -t smartpark-api .
```

Run it, mounting your trained model weights from the host so they are not
baked into the image. This satisfies the "updatable model" requirement:
swap the weights file and restart the container, no rebuild needed.

```bash
docker run -p 8000:8000 -v "$(pwd)/model:/app/model" smartpark-api
```

On Windows (PowerShell):

```powershell
docker run -p 8000:8000 -v "${PWD}\model:/app/model" smartpark-api
```

If you don't mount a model directory, the container still runs fine. It
falls back to the same random-number stub used locally when no
`model.pt` is present.

The `HEALTHCHECK` in the Dockerfile hits `/healthz`. Check container
health with `docker ps`, the STATUS column should say "healthy" after
about 10 seconds.

Note on image size: `ultralytics` pulls in `torch`, so the built image
will be a few hundred MB to a couple GB depending on platform. That's
expected and fine for local Docker testing, but worth knowing before
pushing it to a container registry on a slow connection, since pull time
counts against GKE session cost.

## Deploy to GKE

**First, substitute your own values.** These files contain the author's GCP
project ID (`smartpark-fit3184-508304`), region (`australia-southeast1`) and
model bucket (`smartpark-fit3184-508304-smartpark-model`), which will not
exist in your account:

- `k8s/deployment.yaml`: the bucket name in the `fetch-model` init container
  and the image path in `containers.image`
- `gcp/commands.md` and `gcp/teardown.md`: the project ID, region, repository
  and bucket names

A quick way to replace them all (bash; substitute your own project ID and
bucket, and note that bucket names are globally unique):

```bash
grep -rl "smartpark-fit3184-508304" k8s gcp README.md | xargs sed -i \
  -e 's/smartpark-fit3184-508304-smartpark-model/YOUR_BUCKET_NAME/g' \
  -e 's/smartpark-fit3184-508304/YOUR_PROJECT_ID/g'
```

(The bucket replacement must come first, since the bucket name contains the
project ID.) The region and zone are defined once at the top of
`gcp/commands.md`; change them there and in the commands if you use a
different one.

See `gcp/commands.md` for the full copy-paste command sequence (project
setup, image push, cluster creation, deploy) and `gcp/teardown.md` for
what to run at the end of every session to avoid unnecessary billing.

Key design point: like the local Docker setup, `model.pt` is not baked
into the image. `k8s/deployment.yaml` uses an init container that
downloads it from a GCS bucket into a shared volume before the main
container starts. Swapping the model means re-uploading to the bucket and
restarting the deployment (`kubectl rollout restart deployment
smartpark-api`), not rebuilding the image.

`k8s/hpa.yaml` (autoscaling) is included and has been tested working: under
sustained load it scaled 1 to 4 to 8 replicas within about 20 seconds. It
is NOT applied by default, since it must be removed before Locust
benchmarking at fixed replica counts (see the comment at the top of that
file), otherwise the autoscaler fights your manual `kubectl scale`
commands mid-test. Apply it for general use or for the interview demo:

```bash
kubectl apply -f k8s/hpa.yaml
```

Remove it before running controlled benchmarks:

```bash
kubectl delete -f k8s/hpa.yaml
kubectl scale deployment smartpark-api --replicas=1
```

## Load testing (Locust)

`locust/locustfile.py` simulates users hitting `find-carparks` (weighted
5x) and `annotate-carpark` (1x). `locust/run_sweep.py` automates testing
multiple concurrency levels against one fixed replica count in one
command:

```bash
python locust/run_sweep.py --host http://EXTERNAL_IP --label replicas_1 --users 5 10 20 30
```

Full step-by-step (including per-replica-count warm-up, since each pod
pays a one-time YOLO model load cost) is in `locust/README.md`. "Max
sustainable users" is the highest tested concurrency where the average
response time stayed under 30s (`--latency-ceiling`), matching the report.
Results are saved under `locust/results/`, and `python locust/plot_results.py`
turns them into the report figures.

## Benchmark report

`report/final_report_content.md` is the completed 500-word empirical
report (results table, performance analysis, cost analysis).
`report/figure1_latency_vs_users.png` and
`report/figure2_throughput_vs_users.png` are the two plots in the submitted
report. `report/figure2_p95_latency_vs_users.png` and
`report/figure3_throughput_vs_users.png` were generated from the same data
by `locust/plot_results.py`. `locust/plot_results.py` can also regenerate average latency, p95
latency and throughput figures from the data in `locust/results/`.

Headline findings: 1 to 2 replicas eliminated request failures seen under
load but didn't raise max sustainable concurrency; 2 to 4 replicas
genuinely doubled it; 4 to 8 replicas didn't move it further, evidence
that the fixed 2-node cluster's CPU capacity, not replica count, was the
real ceiling. See the report for full detail.

## Known limitations

- The request log, ops cache and user cache are per pod (see design notes).
- The benchmark figures in the report were measured before the
  `annotate=False` optimisation, the background refresher and the HTTP
  camera call were added. Re-run the sweep if you want numbers for the
  current code, and keep `SMARTPARK_USER_CACHE_TTL` at 0 while doing so.
